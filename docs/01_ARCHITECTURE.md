# Архитектура 0.1

Модульный монолит. React + TypeScript + Vite обслуживается Fastify. Socket.IO передаёт события комнат; серверные операции записываются до ответа клиенту. Excalidraw — редактор; PDF.js — рендеринг страниц; pdf-lib — проверка PDF и экспорт.

## Владение данными

Первый аккаунт — единственный преподаватель-владелец. Ученик создаётся преподавателем и активирует вход через одноразовое приглашение. Гость имеет доступ только к выданной доске. Проверки идут на сервере для HTTP, файлов и подключения к комнате.

Постоянные сущности: users, sessions, students, boards, board_members, pages, operations, snapshots, invites, files, records, audit_events. UUID используются независимо от имени, телефона или почты. `records` хранит типизированные Zod-схемами учебные и организационные записи с owner_id и student_id. Финансовые начисления выводятся из проведённых занятий, а не дублируются второй таблицей балансов.

Данные прежней CRM не мигрировались. Перед интеграцией нужен аудит её авторизации, таблиц, API и идентификаторов; API этой версии не является готовым SSO-адаптером.

## Сохранение доски

Клиент хранит подтверждённую версию каждого объекта и отдельные локальные изменения. Отправляется UUID операции и список изменённых элементов с baseVersion. В транзакции сервер блокирует страницу, проверяет доступ и базовые версии, сохраняет допустимые элементы и tombstones, увеличивает ревизию, пишет результат операции и снимок. Только после COMMIT операция рассылается и подтверждается.

Повтор operationId возвращает прежний результат. Разные объекты сливаются. Для одного объекта устаревший baseVersion вызывает конфликт с возвратом текущего объекта. Клиент сохраняет локальный конфликтный вариант в IndexedDB и предлагает переносимый экспорт. Побуквенного CRDT нет. Удаления не выводятся из отсутствия чужих объектов в переданной сцене.

После reconnect клиент входит в комнату и получает актуальную сцену. Неподтверждённые операции повторяются. Индикатор «Сохранено» зависит от ответа API. Локальный черновик и идентификатор неподтверждённой операции сохраняются в IndexedDB с ключом user_id + page_id. Чужие обновления добавляются без включения в локальную undo/redo-историю редактора.

Во время контакта пера/мыши живой штрих обрабатывает только Excalidraw. Клиент не копирует сцену, не пересчитывает принадлежность пометок и не записывает IndexedDB на каждом движении. После финализации native pointerup микрозадача фиксирует неизменяемую копию только изменённых объектов. Это не позволяет отложенной работе от предыдущего штриха вмешаться в следующий быстрый контакт. Исходное состояние перемещения PDF использует уже зафиксированные объекты без копирования всех прежних точек. События курсора ограничены 20 в секунду и не буферизуются при потере связи. Чужие изменения и обработка HTTP-подтверждений ждут завершения активного жеста; обычное подтверждение сохранения не вызывает повторную установку сцены.

Локальные контрольные точки объединяются с задержкой 120 мс, отправка серверу — 400 мс; работа откладывается, пока идёт жест. IndexedDB версии 2 разделяет данные сцены и неизменяемые бинарные файлы изображений: контрольные точки содержат идентификаторы файлов, бинарные данные сохраняются только при отсутствии в кэше. Прежние черновики версии 1 с вложенными файлами читаются и переносятся без потери локальных правок. Неиспользуемые файлы очищаются при повторном открытии/выходе с доски только при отсутствии неподтверждённого черновика. Проверка наличия и запись файлов выполняются в одной транзакции, поэтому очистка не оставляет новый черновик без изображений.

Снимки: последние 50 на страницу. Журнал идемпотентности в этой версии не ротируется. Перед внедрением ротации нужно согласовать окно офлайн-повтора.

## Файлы и PDF

Файл проверяется по сигнатуре, MIME, размеру; PDF разбирается для проверки числа страниц, изображения — для проверки размеров. SVG, HTML и архивы не разрешены. Имена хранения — случайные ключи, файлы лежат вне web-root. Выдача требует сессии и доступа к доске/учебной записи. Проверка подлинности содержимого не заменяет антивирусную инфраструктуру крупной школы.

Оригинал PDF сохраняется на сервере. Производные PNG собраны в `customData.presentation.slides` одного перемещаемого image-объекта общего холста. `slideIndex` и `fileId` задают активный слайд и синхронизируются обычными элементными операциями. Аннотации имеют `customData.slideAnnotation = {presentationId, slideIndex}`. Неактивные пометки скрываются только проекцией при рендеринге: в сохранённой сцене они не становятся удалёнными. При перемещении/изменении размера презентации связанные пометки преобразуются вместе с ней. При импорте PDF с разными форматами страниц слайды вписываются без растяжения в общую рамку. Остальные картинки слайдов подгружаются при переключении или экспорте сцены. Шрифты, CMaps, WASM и worker размещаются локально.

## Единый холст и фон

`boards.canvas_page_id` указывает на одну каноническую сцену. Протокол страниц остаётся внутренним форматом хранения; системы страниц в интерфейсе нет. `POST /boards/:id/canvas` идемпотентно объединяет старые материалы: обычные страницы раскладываются рядом, страницы одного PDF объединяются в презентацию с отдельными пометками. Исходные дополнительные страницы и их история не удаляются; первая версия сохраняется снимком. Первое преобразование выполняется владельцем при открытии доски. Старые клиенты не могут продолжать писать в дополнительные сцены после объединения.

Фон `boards.background`: white/grid/ruled/dots. Значение проверяется сервером, сохраняется и передаётся участникам событием `board-background`. Экранный рисунок привязан к координатам и масштабу холста; PNG/PDF-экспорт рисует такой же фон под объектами. Смена фона не создаёт тысячи элементов сцены.

Проекция скрытых слайдов и поиск родителей пометок используют индексы по id, а не повторный обход всей сцены для каждой пометки. Если редактор нормализует старые индексы объектов скрытого слайда, сохраняется новая нормализованная версия; отменяется только виртуальное удаление. Это предотвращает цикл бесконечной нормализации и повторных обновлений React.

## Локальный и серверный режим

Без DATABASE_URL используется дисковая PGlite. Это осознанный адаптер для простого запуска на Windows; один процесс API на папку данных. В Docker используется PostgreSQL 17. Оба режима выполняют один SQL-контракт и миграцию без удаления существующих данных. Между форматами нет автоматического переноса базы: перенос нужно делать отдельно с проверкой.

Видео в эту версию не входит и не блокирует ни доску, ни сохранение. Подключение LiveKit/Jitsi проектируется отдельным модулем после испытаний сети.
